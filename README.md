# 局域网快传 v3.4

电脑（浏览器扩展）↔ 手机（Android App）在同一局域网内互传文本、图片与任意格式文件。

## 本次更新（v3.4）

三端版本号已统一：中继 `v3.4`／扩展 `3.4.0`／安卓 `3.4`（versionCode 12）。

**变更**

1. **移除「原图」开关，图片一律原样发送**
   - 该开关只对图片有效、对文件无意义，且容易让人误以为文件也会被压缩，已彻底删除。
   - 扩展端：删除设置页的「图片原图发送」复选框、`background.js` 的 `originalImage`
     配置项，以及 `picker.js` 中的压缩函数；图片与文件现在走同一条「原样读取」路径。
   - 安卓端：`ImageUtils.uriToDataUrl()` 去掉 `original` 参数与压缩分支，保留 MIME 嗅探；
     同时删除遗留的 `PrefsManager.isOriginalImage()` 调用（该方法从未定义，会直接编译失败）。
   - **副作用已处理**：原图保留 EXIF 朝向，而原生解码器不会自动应用，竖拍照片会横躺。
     故新增 `ImageUtils.decodeForDisplay()`，在**显示侧**按 EXIF 旋转，传输内容仍是无损原图。

2. **补齐安卓端批量消息折叠组件**（上一版遗留）
   - 一次选中的多张图片/多个文件共用 `batchId`，界面聚合为一个气泡。
   - 折叠态：两格完整 + 第三格半宽（即「两个半」），总数超过三个时在半格叠加 `+N` 角标。
   - 展开态：每三格一行全部铺开，再点「收起」还原。
   - 缩略图使用独立的低清缓存 `thumbBitmap`，与全屏查看用的 `bitmap` 分开，
     避免批次缩略图把大图缓存降级，导致点开后变模糊。

**校验**

- 资源引用扫描：无未定义项；XML 全部解析通过；括号平衡。
- 跨文件符号扫描：**0 处**待核实引用。
- 扩展端 JS：`node --check` 全部通过。

### v3.2

三端版本号已统一：中继 `v3.2`／扩展 `3.2.0`／安卓 `3.2`（versionCode 10）。

**修复**

1. **安卓端连接状态反复横跳**（反馈的实测问题）
   - 根因：`connect()` 仅在「已连接/正在连接」时复用连接。当处于「失败后退避等待」期间，
     外部（界面恢复、前台服务重启）一调用就重置退避计数并强制重建连接，
     表现为状态在「已连接 ↔ 连接失败」间不停切换。
   - 修复：目标未变时，只要「已连接/正在连接/已排重连」任一成立即复用，且**仅在切换地址或频道时**才重置退避。
   - 同时给状态广播加了**去重**：内容相同的状态不再重复推送，消除瞬态抖动。
2. **补齐缺失的 `sendText()`**：界面调用了该方法而网络层并未定义，属编译级缺陷，已按
   `sendImage`/`sendFile` 的同一套三段式（构造负载 → 发送 → 本地回显）补齐。

**能力校验**

- 中继文件传输端到端测试 **7 项全通过**：文件名、MIME、大小、base64 内容完整一致，
  且新客户端加入时历史补发能还原文件名。
- 大消息（200KB）传输测试通过。
- 三端 JS / XML / YAML 语法校验全通过；跨文件符号引用已自动化核对。

## v2.0 架构：浏览器端改为扩展（MV3）

油猴脚本在每个标签页各注入一份独立实例，开 N 个标签就有 N 条 WebSocket 连接，
导致消息重复、状态不一致、历史不共享。

改为扩展后，连接上移到 Service Worker，**全局唯一**：

```
弹窗（popup）── port ──┐
                        ├─ background.js ── 唯一 WebSocket ── 中继
（可扩展多个 UI）──────┘
```

- 单例连接：无论开多少标签页，只有一条连接
- 消息共享：所有 UI 看到同一份历史（chrome.storage）
- 桌面通知 + chrome.downloads 可靠落盘

## v3.0 变更说明

### 1. 浏览器端：页面面板已移除
删除 content script，不再注入任何网页。全部功能收进扩展弹窗：
聊天、发图、频道管理（进入/切换/离开/发现）、配置（地址/设备名/口令/开关）、图片灯箱。

### 2. 安卓端：修复「同一消息重复显示」
**根因**：`doConnect()` 每次直接覆盖 `ws` 字段却不关闭旧连接；
而 `MainActivity`、`RelayService`、`ShareActivity` 各自触发建连，
最多同时存在 3 条连接且都加入了同一频道 —— 中继给每条连接各广播一次，于是消息重复。

修复：
- `doConnect()` 建连前先关闭旧连接
- 新增 `connecting` 单飞标志，并发调用只建一条
- `connect()` 同地址同频道则复用，不重建
- `ensureConnected()` / `isActive()` 收敛判断，三处入口统一
- 防御性去重：按服务端消息 ID 丢弃重复投递

### 3. 安卓端：界面升级
- 建立 `colors.xml` / `themes.xml` 统一深色主题（Tokyo Night 配色）
- 气泡改为带「尾巴」的不对称圆角，文字颜色随气泡背景自适应
- 顶栏改为圆形图标按钮，输入框圆角化，发送改为圆形按钮
- 图片消息圆角裁切，通知改用应用图标并统一主题色
- 连接状态条按状态着色（绿=已连接）

### 4. 中继：补齐持久化
- **消息 ID**：每条消息分配稳定 ID，客户端据此去重（重连补发不再重复渲染）
- **修复口令持久化**：此前的 `saveState()` 只写 `history.json`，
  导致 `channelRules`（频道口令）从未落盘、重启即丢。现两个文件都写，且采用临时文件 + 重命名原子写
- **新增 `setpassword` 认领入口**：此前 `setChannelPassword` 无任何调用点，
  口令功能实际不生效。现在客户端设口令时会向中继认领，口令不一致的客户端将被拒绝加入
- 新增 `GET /history?channel=xxxx` 按需拉取历史
- 历史回补时保留消息 ID 与发送者信息，重启后历史不丢

## 单文件体积上限与改进方向（v3.4 现状）

### 当前上限：约 24MB

| 环节 | 限制 | 位置 |
|---|---|---|
| 中继单条消息 | 32MB（JSON 文本，即 base64 **之后**的体积） | `relay-standalone.js` 的 `--limit`，默认 32 |
| 实际可传原始文件 | **约 24MB**（base64 膨胀 4/3：32 ÷ 1.333 ≈ 24） | 由上式换算 |
| 扩展端软限制 | 20MB（原始文件），超出跳过并提示 | `picker.js` 的 `SOFT_LIMIT` |
| 安卓端软限制 | 20MB（原始文件） | `MainActivity` 的 `softLimit` |
| 历史落盘阈值 | 正文 > 256KB 不写入 `history.json`，仅存元数据 | `HEAVY_SKIP` |
| 每频道历史总量 | 8MB | `CHANNEL_BYTES` |
| 速率限制 | 100 条 / 60 秒（批量发送时一图/一文件占一条） | `RATE_LIMIT` |
| 接收缓冲保护 | 单连接缓冲 > 64MB 直接断开 | 中继背压保护 |

**两个容易被忽略的后果**

1. **大文件重启后只剩“空壳”**：超过 256KB 的正文不落盘。中继重启后补发的历史里只有文件名与大小，
   内容标记为「已不可回补」，界面上该文件会置灰、不可点击。实时收发不受影响，仅影响历史回溯。
2. **安卓端内存峰值偏高**：图片改为原图直传后，一个 24MB 文件会同时存在
   原始字节数组（24MB）+ Base64 字符串（约 64MB，Java String 为 UTF-16）+ 组装中的 JSON（再约 64MB），
   峰值可超 150MB，低端机有 OOM 风险。这是「图片不再压缩」后被放大的既有问题。

### 改进方向（按性价比排序）

1. **分片传输**（推荐优先）
   客户端把大文件切成 256KB~1MB 的块逐块发送（`fileId` + `chunkIndex` + `chunkTotal`），
   接收端按 `fileId` 重组。收益：突破单条上限、内存平稳、可显示进度、支持断点续传。
   代价：协议与三端收发逻辑都要改，中继需新增分片透传。

2. **HTTP 上传 + 消息引用**（最彻底）
   中继已有 HTTP 服务，加两个接口即可：`POST /upload`（写磁盘返回文件 ID）、`GET /f/:id`（下载）。
   消息里只带 `{ type:'file', fileId, name, size, mime }`，接收端按需下载。
   收益：几乎不受体积限制、不占 WebSocket 内存、历史可长期保留、天然支持断点。
   代价：中继需管理文件生命周期（过期清理），接收端增加下载逻辑。

3. **二进制帧（opcode 0x2）**
   直接传字节而非 base64，省约 33% 带宽与内存。但仍受单条上限与内存峰值约束，属治标。

4. **提高 `--limit`**
   一个参数即可放大上限，但内存与 OOM 风险同步放大，只建议在大内存机器上临时使用。

5. **中继流式转发**
   收到帧头后边收边转，不缓存整条消息，能显著削峰；但要改动帧处理主循环，复杂度最高。

> 若主要传照片和常见文档，**当前 20MB 软限制基本够用**；
> 若要传视频、压缩包或安装包，建议直接上方案 2。
